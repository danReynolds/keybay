## 1. Verdict in brief

The shared-engine / platform-adapter architecture should **remain**. I found no path by which caller input, unauthenticated store bytes, or persisted provider state can redirect identity, file location, provider, or deletion authority, and no path that returns plaintext before authentication. The cryptographic transcript matches the RFC and the independent Go reference. The engine's ordering rules (pinned generations, copy-forward digests, epoch-bound frame AAD, fail-closed reset phases) held up under adversarial reading, the existing adversarial suites, a fresh 3,000-case fuzz run, and real process-kill and provider lanes on this host.

Corrections are **bounded**, not architectural:

### 4.1 Confirmed defects

#### KB-CR-001 — Intel (x86_64) macOS fails closed on every file operation because the plain `fstat` symbol is the legacy ABI

- **Severity:** Medium (availability of a documented-supported platform; no unsafe acceptance).
- **Files:** `packages/keybay/lib/src/v2/posix_store_files.dart:1629-1633` (`_darwinFstat` looks up `'fstat'`), `:1315-1320` (ABI allowlist explicitly admits `Abi.macosX64`), `:1509-1556` (`_DarwinStat` declares the 144-byte 64-bit-inode layout: mode at offset 4, size at offset 96).
- **Trust boundary / preconditions:** none; any process on an Intel Mac (or an x86_64 Dart/Flutter build under Rosetta).
- **Mechanism:** On x86_64 Darwin, libSystem exports two ABIs: the plain `fstat` symbol keeps the legacy layout (32-bit `st_ino` at offset 4, `st_mode` at offset 8, `st_size` at offset 72) for binary compatibility, while compiled C code is mapped by the headers to `fstat$INODE64`, which uses the layout the code declares. On arm64 only the 64-bit-inode ABI exists and the plain symbol is correct, which is why every macOS CI job (`macos-latest`, `macos-15`, both arm64) and the maintainer's machine pass.
- **Reproduction (`receipts/fstat-abi-probe-output.txt`):** for `/etc/hosts` (mode 100644, 365 bytes):
  - arm64, symbol `fstat`: Keybay layout reads mode `100644`, size `365` (correct).
  - x86_64 under Rosetta, symbol `fstat`: Keybay layout reads mode **`55033`**, size **`0`**; the legacy offset 8 holds the real mode.
  - x86_64, symbol `fstat$INODE64`: mode `100644`, size `365` (correct).
- **Impact:** `_validateDescriptor` requires exact type and permission bits, so root, lock, staging and live descriptors all fail with `operationFailed` → `storageOperationFailed`; `Keybay.open()`, `reset()` and every record operation are unusable on Intel Macs. Because the misread value is the low inode bits, a spurious pass is possible only with probability ~2/65,536 per directory open and never yields a wrong file (the descriptor was already opened with `O_DIRECTORY`/`O_NOFOLLOW`; a file's misread size of 0 fails the minimum-length check). So this is fail-closed, not fail-open.
- **Smallest adequate correction:** resolve the symbol by ABI: `Abi.current() == Abi.macosX64 ? r'fstat$INODE64' : 'fstat'` (the iOS x86_64 simulator uses only the 64-bit-inode ABI and is believed unaffected, but should be covered by the same regression). Do not use `fstat64` (deprecated).
- **Regression/qualification:** add an x86_64 macOS job (Intel runner, or an x64 Dart SDK executed under Rosetta on an arm64 runner) running at least `v2_posix_store_files_test.dart` and the macOS native lane; add a unit test that compares `_readDescriptorMetadata` output with `FileStat` for a known file on every Apple ABI. Until then, public docs must say macOS support is qualified on Apple Silicon only.

### 4.2 Product limits and documentation errors (reviewable exclusions)

#### KB-CR-002 — Root-only state after uninstall/reinstall on iOS and entitled macOS is a normal lifecycle outcome, but the SDK guide does not tell integrators to handle it

- **Severity:** Medium (product suitability / misleading by omission; not a confidentiality issue).
- **Files:** `framed_store_writer.dart:104-117` (`adopted` root → `storeStateConflict`), `apple_data_protection_keychain_protector.dart:70-86` (`createIfAbsent` duplicate → `adopted`), `doc/platforms/ios.md` (documents the behavior), `doc/sdk.md:157-169` (error-code list omits `storeStateConflict`).
- **Behavior (verified by test "same signed iOS identity refuses an empty second container" and by the RFC's state machine):** Data Protection Keychain items survive app deletion on iOS and macOS while the container does not. After reinstall, `Keybay.open()` finds a retained root with no live file and returns `storeStateConflict`; it will keep doing so until the application calls `Keybay.reset()`. The same root-only state arises after a same-device restore from an encrypted backup (the file is backup-excluded; `ThisDeviceOnly` items restore to the same device), and on desktop after any failure between provider-root creation and the first durable file commit (`_initializeStore` creates the root before staging and does not roll it back). These are deliberate RFC choices ("Root-only … fail closed", "deliberate reset is the recovery path"); the qualification report honestly lists reinstall/restore as unqualified (`KB-INV-004`, `KB-INV-008`).
- **Why it is reviewable:** the choice is defensible on desktop (a missing file may be tampering), but on iOS it turns a routine user action into a permanent `open()` failure unless every integrator writes a reset-on-conflict branch. The quickstart in `doc/sdk.md` and both READMEs present `Keybay.open()` as sufficient and never name `storeStateConflict`; only `doc/platforms/ios.md` explains it. A developer following the guide ships an app that stops working after one reinstall.
- **Smallest adequate correction (no runtime change):** in `doc/sdk.md` add `storeStateConflict` to the important codes with the exact expected handling for iOS/entitled macOS (call `Keybay.reset()` when the app knows it has no local data, then reopen), state that the same applies after a same-device restore and after an interrupted first initialization on any profile, and repeat the note in `doc/platforms/macos.md` for the entitled profile. Optionally make the `KeybayException.message` for this specific case say "platform root exists without a store" so integrators can distinguish it in logs (the code is already `storeStateConflict`; a new enum value would be an API change and is not required).
- **Qualification:** physical reinstall and restore-to-same-device phases remain pending in the mobile procedures; this review does not supply them.

#### KB-CR-005 — Public statements that lag the evidence or omit a caveat

- **Severity:** Low (documentation).
- Items:
  1. `SECURITY.md` ("neither hermetic tests nor Docker establish it") and `doc/platforms/linux.md` ("The configured native Ubuntu x64 CI lane has not yet run against this snapshot") predate the native Ubuntu 24.04 x64 CI pass recorded in `doc/qualification-status.md`; `START_HERE.md` already flags the first.
  2. `doc/platform-regression.md` still says physical `--upgrade`/`--crash` execution "remains pending"; both passed on 2026-09-06 per the qualification report and receipts.
  3. No document restricts macOS support to Apple Silicon, and CI runs only arm64 macOS runners (KB-CR-001).
  4. `doc/sdk.md` omits `storeStateConflict` and the reinstall/restore handling (KB-CR-002), and omits the RFC's documented fact that `Keybay.open()` fails closed with `applicationIdentityUnavailable` under the `package:test` runner (confirmed here), which matters to integrators writing their own tests.
  5. RFC 0001 and `SECURITY.md` describe Argon2 working memory as managed memory that "cannot be promised perfectly overwritten"; the pinned implementation actually uses native `calloc` memory that can be overwritten (KB-CR-003).
  6. The "record operations never prompt" statement in `doc/sdk.md`, `SECURITY.md` and `doc/architecture.md` is unqualified by Secret Service implementation (KB-CR-004); the platform page correctly says only gnome-keyring is qualified.
- **Correction:** edit the six statements; none changes runtime bytes.

### 4.3 Hardening with concrete benefit

#### KB-CR-003 — Zero the Argon2 working buffer before releasing it; correct the memory-clearing claim

- **Severity:** Low (narrows a documented residual risk; corrects a public claim).
- **Files:** `passphrase_kdf.dart:155-206` (`_runV2PassphraseDerivation`, `state.tryReleaseMemory()` at line 187); dependency `cryptography-2.9.0/lib/src/dart/argon2_impl_default.dart` (`getByteBuffer()` allocates `1024 * blockCount` bytes with `malloc`, attaches a finalizer; `tryReleaseMemory()` calls `calloc.free` without overwriting), `argon2.dart` (`_getOutput()` derives the 32-byte result from the XOR of the last column, so the buffer contents suffice to recompute `Kpass`).
- **Evidence (`receipts/argon2-native-buffer-probe.txt`):** after a production-profile derivation, 16,315 of 16,384 sampled pages are nonzero; after `tryReleaseMemory()` the (now freed, not yet reused) native memory still holds them. Zeroing the buffer through the public `getByteBuffer()` view before release took 121–128 ms on this host and left zero nonzero pages. Derivation itself took 265–277 ms idle here and 3.5 s on the Pixel 6a receipt, so the relative cost is small.
- **Why it matters:** the buffer is the largest passphrase-derived artifact in the process, it lives in unmanaged memory (so, unlike Dart heap copies, overwriting is deterministic), and the RFC's stated reason for not clearing it ("managed working memory") is inaccurate for this implementation.
- **Smallest adequate correction:** in `_runV2PassphraseDerivation`, before `state?.tryReleaseMemory()`, do `state.getByteBuffer().asUint8List().fillRange(0, length, 0)` inside the existing cleanup try (best-effort; it also works when the dependency falls back to a heap buffer). Update RFC 0001 and `SECURITY.md` to say the working buffer is overwritten by Keybay before release while dependency-internal Blake2b/HMAC state and VM copies remain out of scope.
- **Regression:** extend `v2_crypto_dependency_test.dart` with a case asserting that `getByteBuffer()` is addressable after `deriveKeyBytes` and that Keybay's wrapper leaves it zero (a small test seam on the deriver, or a dependency-level assertion that documents the assumption).

### 4.4 Plausible concerns needing evidence

#### KB-CR-004 — The Linux stale-session recheck can reach a Secret Service implementation that prompts

- **Severity:** Low; unproven here (no KWallet/KeePassXC host available); qualification-scoped.
- **Files:** `linux_secret_service_protector.dart:47-55` (`openExisting` does not consult `interaction`), `framed_store_reader.dart:769-782` and `:829-886` (`_hasNewerAuthenticatedGeneration` opens the provider with `PlatformInteraction.forbidden` from the record-operation failure path), `v2_linux_secret_service_protector_test.dart` (codifies that the Linux protector proceeds under `forbidden`).
- **Reasoning:** the no-prompt property for Linux record operations is not structural; it relies on the provider never showing UI for `SearchItems`/`OpenSession`/`GetSecret` on an unlocked collection. That holds for gnome-keyring (the only qualified backend) but not for every `org.freedesktop.secrets` provider: KWallet's Secret Service front end asks the user to authorize an application's wallet access, and KeePassXC's integration has an opt-in "confirm when passwords are retrieved" dialog. On such hosts a tampered or peer-rotated store would trigger UI during `get`/`set`, bounded only by Keybay's 15 s D-Bus timeout, contradicting the unqualified public statement. Nothing falls back or returns plaintext; the risk is the interaction contract, not confidentiality.
- **Options (owner's decision):** (a) minimum: make the Linux protector refuse `forbidden` acquisitions before any D-Bus call, exactly as the classic macOS profile does (`macos_login_keychain_protector.dart:119-125`), accepting that cross-process rotation on Linux is then reported as `storeAuthenticationFailed` rather than `staleSession`; (b) simplification: remove the cross-process recheck entirely (≈60 lines), making "record operations never touch the provider" true by construction on every profile and deleting the only provider access on the record path; (c) documentation only: qualify the public claim as gnome-keyring-specific. I recommend (a) now and considering (b) as a justified-simplicity change; both need an interaction-contract test asserting the Linux protector throws `interactionRequired` under `forbidden`.

### 4.5 Design observations and preferences (Info)

- **KB-CR-006 — Provider UI and Argon2 run while the 1 s file lock is held.** `_commitAuthChange` acquires the root with UI permitted and derives the passphrase key inside `withExclusiveTransaction` (`framed_store_rotation.dart:73-83`, `:175-180`); `_initializeStore` derives before creating the root but still inside the transaction (`framed_store_writer.dart:74-79`); `_open` with an abandoned stage authenticates under the lock (`framed_store_reader.dart:182-190`); `reset` prepares the provider under the lock (`framed_store_writer.dart:270`). Concurrent processes receive `storeBusy` after one second and must retry (the Android harness retries for 30 s). Not a defect; document the retry expectation, or acquire the root and derive before taking the lock where the validation already re-checks state.
- **KB-CR-007 — Stale classification under contention.** If the classification recheck cannot take the lock within 1 s (e.g. the rotating process is still verifying), the operation reports `storeAuthenticationFailed` rather than `staleSession`. Integrators should treat both as "close and reopen"; worth one sentence in the guide.
- **KB-CR-008 — Post-rename verification for ordinary writes accepts any generation with the expected record count**, not the exact staged bytes (`framed_store_writer.dart:503-512`). Rotation's post-rename check is exact because only the staged file authenticates under the new key. Within the same-user threat model this is fine; comparing the installed manifest ciphertext with the staged manifest would make acknowledgement exact at negligible cost.
- **KB-CR-009 — `package:test` fail-closed identity confirmed** (`Platform.script` is a temp `.dill`; `Isolate.packageConfig` points outside `.dart_tool/pub/bin`). Downstream applications cannot exercise `Keybay.open()` in their own test suites on desktop; the RFC states this, the SDK guide does not (folded into KB-CR-005).
- **KB-CR-010 — `_fcntl` is bound with a non-variadic signature** for `F_FULLFSYNC` (`posix_store_files.dart:1619-1622`) while `portal_secret_pipe.dart` binds `fcntl` with `VarArgs`. Harmless in practice on both ABIs (no variadic argument is read for that command), but the x86_64 SysV convention expects `%al` to be set for variadic calls; use `VarArgs<(Int32,)>` for consistency when touching the file for KB-CR-001.
- **KB-CR-011 — Argon2 helper isolates.** The pinned implementation spawns four helper isolates per derivation sharing the native buffer by address and kills them afterwards; `doc/design.md`'s "serialized per isolate" statement concerns the caller queue and is correct, but the resource note may help mobile integrators (the Pixel 6a receipt's 351 MiB whole-app peak RSS includes this).
- **Simplicity notes (no action required):** the `getManyBytes` aggregate bound (16 MiB) is unreachable because the file bound is 16 MiB; `openPlatformOnly()` is a compatibility alias; `_sameBytes`/`_clear` are duplicated across six files; HKDF sub-keys are re-derived on every operation (defensible: no additional long-lived key copies). The POSIX adapter's size is dominated by failure-precedence and descriptor cleanup, which I judged necessary rather than accidental.

## 5. Boundaries inspected and what held

**Public API and composition** (`keybay_v2.dart`, `host_platform.dart`, `host_binding.dart`): no selector, path, provider or identity input exists on the public surface; `ResolvedHost` refuses adapters that do not share the identical binding object; the storage-domain commitment and provider address encodings match the RFC (label, NUL, length-prefixed identity, one-byte assurance wire code, profile, location; provider address excludes the location). Credential snapshots are taken synchronously and cleared on every path; validation failures are delivered through the future. `src/` imports can of course bypass the public surface, as in any Dart package; the CLI uses only the public library.

**Transcript, decoding and KDF** (`format/`, `passphrase_kdf.dart`): all bounds precede allocation and cryptography (provider state ≤ 64 B, package 1–4096 B, file ≤ 16 MiB, trailer 44–655,404 B, manifest ≤ 4,096 entries × ≤ 120-byte keys, frame 40–1 MiB+40 B, epoch 1..2^63−1, profile ID allowlisted before Argon2, passphrase 1–1024 B before Argon2). AAD transcripts and HKDF labels match the RFC and the Go reference byte-for-byte. Frame AAD binds store ID, epoch, type and exact key and excludes layout, so copy-forward is byte-identical and not a nonce reuse. The pinned AEAD decrypts in place into Keybay's workspace before comparing the tag; both opening paths clear that workspace in `finally`, and the successful result aliases the workspace and is copied out before clearing (`_concatenate` returns the single chunk). Canonical decoding rejects duplicates, non-ascending keys, gaps, overlaps and trailing bytes.

**Session and transaction engine** (`framed_store_reader/writer/rotation.dart`): reads pin one descriptor and never reopen; manifest and every selected frame are authenticated before any value is released; writes stream every source frame through SHA-256 against the authenticated manifest, copy unchanged ciphertext, verify the staged snapshot, replace atomically, then verify the committed generation; rotation decrypts and reseals one frame at a time under the new epoch and classifies old/replacement/unknown on post-rename failure, invalidating peers only when unknown; reset prepares the provider without mutation, revokes the live name first, then commits and reports `resetIncomplete` for anything after revocation; same-runtime invalidation is generation-based and drained outside the lock (no deadlock path found). The RFC's open matrix, `protectionMismatch` refusal of an attacker-created platform-only replacement, and live-plus-stage cleanup ordering are implemented as specified.

**Filesystem ownership** (`store_files.dart`, `posix_store_files.dart`): component-wise `openat(O_DIRECTORY|O_NOFOLLOW)` walk from `/`, descriptor-relative fixed names, `O_CREAT|O_EXCL` staging, `fchmod` after create (umask-proof), macOS extended-ACL clearing and rejection, Linux mode check via `/proc/self/fd` (which also surfaces effective POSIX ACL masks), `fsync` plus `F_FULLFSYNC` on Darwin for files and the directory, `renameat` under `flock`, symlink/FIFO/directory impostors rejected (`_entryExists` treats `ELOOP` as present so a planted symlink is a typed failure, never a redirect). Reset retains the lock inode deliberately. The staging name's create-only semantics provide mutual exclusion for mutations even where `flock` is weak (network filesystems), which is a good property worth stating in docs.

**Provider lifetime** (`platform_protector.dart`, `exportable_root_lease.dart`, `exportable_root_protector_core.dart`): interaction permission is fixed per acquisition; root bytes are operation-lived and cleared on lease close; provider state is a domain-separated fingerprint of the root (or Android's GCM-sealed domain), so a replaced root is `invalidated` before any package open; create is insert-only with exact read-back and `adopted` otherwise; prepared resets are digest-pinned and single-use; deletion is exact by address. Secret Service and classic Keychain lack compare-and-delete, and the docs say so.

**Platform authority and native ABI** (`application_identity.dart`, `*_host_platform.dart`, `*protector.dart`, `*root_store.dart`, `ffi/`): declared identity comes only from the owning pubspec (narrow parser, 64 KiB bound, strict UTF-8, exact block grammar), the activation root, a recognized `dart install` bundle, or a compile-time embedding that must agree with any metadata; `.dill` test bootstraps and unrecognized AOT launches fail closed (verified). iOS binds the signed `KeybayApplicationIdentifier` (raw processed Info.plist, not the localizable accessor) to the exact Keychain group and a container-relative domain; the Keychain enforces the group, so the declaration cannot select another team's items. macOS dispatch reads `com.apple.application-identifier` / `application-identifier` through `SecTask` and refuses group-only entitlements; the classic profile pins `login.keychain-db` via `SecKeychainOpen`, `kSecUseKeychain` and a one-entry search list. Android derives package/UID from `java.io.tmpdir` and `Application.getProcessName()` with strict grammar and `Os.stat` ownership/mode checks, and uses one AES-256-GCM non-exportable key with StrongBox attempted and a documented fallback; JNI is local-frame scoped, exceptions are classified without copying messages, byte arrays are zeroed. Apple FFI pairs every `Create` with `CFRelease`; CF constants are read as symbol values. Open-flag ABI constants are per-architecture and fail closed on unknown ABIs. The one ABI defect found is KB-CR-001.

**Portal and D-Bus** (`linux_secret_portal.dart`, `portal_secret_pipe.dart`, `linux_secret_service_root_store.dart`): the portal path pins the owner's unique name, uses a random `handle_token` request path, installs the signal subscription and an explicit `AddMatch` before `RetrieveSecret`, checks sender/path/interface/member/signature on every signal (the `dbus` package fills `sender` from the message header, which the bus sets), rejects any `token`, bounds the secret to 4096 B with an overflow byte, requires non-empty EOF, re-verifies the owner after completion, sends `Request.Close` on abort, and never falls back. The Secret Service path uses fixed destinations, `allowInteractiveAuthorization: false`, exact reply signatures, object-path prefix checks, one fresh connection and one total timeout per operation with a lifetime guard against late replies, no `Unlock`/`Prompt`/`CreateCollection`. All three real-D-Bus transport tests and the two-app Flatpak lane passed in Docker here.

**Adequacy of stated exclusions:** the same-user desktop limit, rollback non-goal, Flatpak retained secret, live-memory exclusion and root/hostile-code exclusions are stated consistently across RFC, design, SECURITY and platform pages and are appropriate for a local store. Two exclusions deserve sharper wording: Flatpak isolation "assumes default confinement" (a `--filesystem=home` plus `--talk-name=org.freedesktop.secrets` app can reach a peer's files and portal secret; the page's general sentence covers it but naming those grants would help), and the memory-clearing statement (KB-CR-003).

## 6. Reassessment of SR-001 through SR-004

- **SR-001 (portal read keeps process alive) — resolved and sound.** `PortalSecretPipe` creates the pipe with `O_CLOEXEC` (`pipe2` on Linux; `F_SETFD` on macOS), makes only the read end nonblocking with the correct per-OS `O_NONBLOCK`, opens the write end through `/proc/self/fd` or `/dev/fd` (no filesystem node), and closes the original write descriptor immediately; the reader is a 2 ms timer that stops on EOF/failure; `_cleanup` closes the reader synchronously and zeroes and frees the native buffer; timeout sends `Request.Close` with a 100 ms grace before closing the connection. Residual: a hostile provider can still hold its copy of the write end indefinitely, which the docs state; polling at 2 ms for up to 60 s is a bounded cost. Docker Flatpak lane here passed the prompt cancellation, timeout and descriptor-retention cases.
- **SR-002 (hardened single-file executable killed at startup) — accurately bounded.** This is a Dart runtime loader behavior, not an SDK defect; the qualified runtime/module pair is a legitimate distribution shape; the single-file form is correctly reported as failed and product packaging is deferred. No SDK change warranted. Keep the failure receipt public.
- **SR-003 (separate native AOT module identity) — resolved and sound.** `_canonicalAotImage` sniffs ELF/Mach-O magic only to *classify* the launch and still requires the compile-time embedded declaration; it derives nothing from path, header or environment, and a conflicting `dart install` declaration fails closed. A fat Mach-O module (`0xcafebabe`) is not recognized and fails closed, which is acceptable. The namespace-only claim is unchanged.
- **SR-004 (HKDF result not overwritten) — correct and appropriately scoped.** Confirmed at `hkdf.dart:75` (`SecretKeyData(result)` without `overwriteWhenDestroyed`). Keybay copies into its own overwritable buffer and destroys the wrapper; residual exposure is one immutable 32-byte copy per derivation plus HMAC internals, GC-lifetime. The same class of finding applies to Argon2 with the important difference that its buffer is native and can be cleared (KB-CR-003); the documentation correction should cover both.

## 7. Architecture judgement

**Keep the shared-engine / platform-adapter design; apply bounded corrections.** The evidence: (1) every authority decision (identity, location, provider, deletion target) is made before any store byte is read and is bound into AAD and provider records, and I found no persisted or caller input that can move it; (2) the framed snapshot with an authenticated tail manifest, exact-frame digests and epoch-bound frame AAD gives selective decryption, byte-exact copy-forward and full re-encryption on policy change without a journal or database, and the independent Go vectors, adversarial suites, 3,000-case fuzz run and real process-kill tests exercised exactly those properties; (3) the one confirmed defect is a single-symbol ABI lookup in an adapter, and the remaining findings are documentation and policy choices, none of which would be easier to fix in a different architecture. A material redesign is not justified by any evidence I gathered. The only structural simplification I would consider is removing the cross-process stale recheck (KB-CR-004 option b), which deletes provider access from the record path on every profile.

## 8. Release-blocking versus deferred

**Blocking before a release that claims the current platform list:**
1. KB-CR-001: fix the x86_64 `fstat` symbol and add an x86_64 macOS regression, or restrict the macOS claim to Apple Silicon.
2. Documentation edits in KB-CR-002 and KB-CR-005 (no runtime change).

**Recommended before release, not blocking:** KB-CR-003 (Argon2 zeroing plus claim correction); KB-CR-004 option (a) plus its test; KB-CR-006/007 guidance sentences.

**Deferred product features (unchanged by this review):** rollback anchors, platform-root rotation, multiple/hardware unlock methods, Snap, Windows, single-file hardened CLI packaging.

**Missing evidence that remains missing:** physical lock/reboot/first-unlock, physical auth-change interruption, backup/restore/transfer on Android and iOS (`KB-INV-004`, `KB-INV-008`), reinstall/restore root-only behavior on a device, Intel macOS (any lane), Xcode 16.4 (my iOS lane ran under 26.6), maintained-device Argon2 acceptance budgets (no budget exists; this host measured ~270 ms / ~178 MiB), StrongBox-specific assertion, non-gnome-keyring Secret Service providers, Fedora-style symlinked home under Flatpak. CI success, the pack, and this report are not release approval.
